## Subsequent releases

The reviewed operator scripts are installed as root-owned files at `/opt/firelaunch-staging-ops/` on muffinos. Build an archive with `build-release.sh`, record its SHA-256 independently, copy the archive and `.sha256` companion to `/home/deploy/firelaunch-incoming/`, and run `deploy-release.sh` from the protected operator directory with the independently recorded hash. It accepts only schema-compatible releases, verifies the protected layout and HTTPS health, makes an encrypted backup, then switches `/srv/firelaunch/current` atomically. The scripts must not run from a deploy-writable checkout.

For a schema-compatible bad release, the protected `rollback.sh` uses the verified `/srv/firelaunch/previous` recorded by the successful 2026-10-17 Add Video scripted deployment. The former manual-consolidation recovery requiring Nginx changes and revival of `firelaunch-alpha-067.service` is **historical only** and must NOT be the default rollback. Use the approved command-specific operator mechanism, verify target/current release and schema compatibility, and confirm authenticated health afterward. Keep the retired port-4185 service and schema-10 database offline; never run schema-10 binary 0.5.8 against schema 13. Rollback that changes schema/objects requires a separately authorized rehearsed procedure.

The successful Add Video deployment also made a protected encrypted predeploy schema-13 archive (recorded in its closeout). The backup helper currently archives the database and `private_objects`, not managed-video originals. Protect and verify those S3 objects separately before any future media recovery or destructive storage change. Do not infer production or playback qualification from this staging upload deployment.
