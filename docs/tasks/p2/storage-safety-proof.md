# P4 private storage safety proof (0.2.4)

The P4 implementation adds `private_objects` metadata constraints and hashed, expiring `private_object_capabilities` in Postgres migration 003. The service validates a verified principal against provider identity and project ownership before using a private object reference. Object IDs and physical keys use independent random values; HTTP metadata excludes the physical key. Download requires both the authenticated session and a 60-second capability. Revocation and deletion invalidate capabilities; object deletion cascades capability rows. Hosted startup requires server-only S3 credentials and HTTPS for a custom endpoint. S3 operations use PutObject, GetObject and DeleteObject with AES256 server-side encryption and no ACL or list calls. The isolated file adapter is gated to `NODE_ENV=test`.

Executed on 2026-10-10 with Node 24.21.0, npm 11.19.0, local isolated PostgreSQL 16.15 on port 55432, and a fresh temporary object directory. Command: `FIRELAUNCH_TEST_DATABASE_URL=postgresql://jfin@127.0.0.1:55432/postgres node --import tsx --test apps/server/test/private-objects.test.ts apps/server/test/hosted-repository.test.ts`. Result: 3 tests passed, 0 failed, 0 skipped. Assertions covered two account identities, forged account IDs, guessed object IDs, foreign project IDs, API cookie/CSRF and cross-owner download, tampered capability, 60-second expiry, revocation, deletion, invalid type and size, failed metadata insert orphan cleanup, key and capability hashing, private response redaction, restart and migration rollback. No external S3 bucket or real hosted identity was exercised; those remain P7 qualification gates. P6 owns persistent orphan reconciliation and database-plus-object backup/restore.
