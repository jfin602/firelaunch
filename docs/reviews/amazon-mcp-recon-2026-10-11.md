## 5. Vega SDK and VPKG Findings

**OS 1.2: OK.** SDK 0.24 requires `[os.version]` with minted `min` and `target`; the template has both `1.2` and `/com.amazon.vega.os@IVega_1_2`, matching [Amazon's example](https://developer.amazon.com/docs/vega/0.24/manifest-os-version). The c0 candidate passed Vega doctor/VPT according to its preserved record. This audit did not rebuild the current source.

**Release lineage: F-02.** [The template](/home/jfin/dev/firelaunch/templates/vega-channel/manifest.toml:5) fixes version `0.0.2`; [the generated build script](/home/jfin/dev/firelaunch/packages/generator/src/index.ts:40) and [local build command](/home/jfin/dev/firelaunch/apps/server/src/workspace.ts:222) pass neither `--build-version` nor `--build-number`. Amazon says the VPKG build number must increase for Appstore updates and can be inspected with `vega exec vpt info ... --json` ([version guide](https://developer.amazon.com/docs/vega/0.24/app-version.html), [submission](https://developer.amazon.com/docs/vega/0.24/app-submission.html)). This does not invalidate the one c0 candidate; it prevents truthful repeat-release readiness unless P7 supplies lineage. Do not treat remote manifest sequence as VPKG build number.

Generated dependency ranges (`~4.0.0`, `~2.3.2`, `^0`) and no generated lockfile mean a later `npm install` can resolve a different package set for the same source tree ([generator](/home/jfin/dev/firelaunch/packages/generator/src/index.ts:41)). This is reproducibility debt, not evidence of an invalid current package. Keep install/toolchain/package identity in artifact provenance.

## 7. TV, Media, and Update Findings

The generated player's `initialize` → surface attach → source and surface detach → `deinitialize` sequence follows Amazon's basic URL-mode video example ([playback guide](https://developer.amazon.com/docs/vega/0.24/media-player-select-playback.html)). It has no `AppState` listener, player error event, failed-init branch, or foreground recovery path ([App](/home/jfin/dev/firelaunch/templates/vega-channel/src/App.js:7)). Amazon recommends stopping playback and releasing decoders when backgrounded ([lifecycle](https://developer.amazon.com/docs/vega/0.24/foreground-background.html)). This is F-03. Captions/audio-description behavior, DRM, stream formats, actual media rights and device compatibility remain unqualified; a simple MP4/MP3 player should not be described as HLS/DASH/DRM support.

Custom focus state gives visible D-pad semantics and c0 proved a bounded candidate, but `focusable={false}` appears on every generated Pressable ([App](/home/jfin/dev/firelaunch/templates/vega-channel/src/App.js:50)). Amazon's native focus and accessibility guidance uses focusable/accessible controls and focus restoration ([focus guide](https://developer.amazon.com/docs/vega/0.24/focus-management.html)). This is F-05, a review/target-test item; it does **not** establish a confirmed current D-pad failure because FireLaunch deliberately dispatches TV commands itself. `ScrollView` visibility under that custom focus model also needs target observation.

P5's remote content plan is technically compatible with an installed native Vega app if the app fetches approved HTTPS data and validates compatibility. The current generated app is static, so [publication schemas](/home/jfin/dev/firelaunch/packages/contracts/src/publication.ts:52) are only an early contract. Amazon package-management docs describe VPKG installation separately from data delivery; a successful remote fetch must never be reported as a VPKG update ([package tools](https://developer.amazon.com/docs/vega/0.24/app-management-com-tools.html)). Native/permission/runtime changes still require an actual new package and applicable Appstore review.

## 10. Phase 5 Impact

**Proceed with amendments**, not unchanged and not globally blocked. The Amazon foundation is credible: RN 0.83, SDK 0.24 OS 1.2 manifest, native W3C player, release build wrapper, and creator-owned app concept fit official guidance. P5's immutable HTTPS manifests, compatibility checks, last-known-good cache and rollback are sensible application design; no official source found here requires a new binary for each compatible data change. Their success must be measured in the same installed VPKG, not inferred from browser Preview or test contracts. F-01 should be the first P5 contract correction. F-03 belongs before a P5 TV GREEN claim if media playback participates in the qualification path. F-02 is a P7 repeat-binary release requirement and should be represented in P5 deployment metadata; it does not prevent building the P5 remote-content prototype.

Do not substitute optional platform integrations for the small core client. Use Amazon's W3C media player, native focus tools where they improve accessibility, VPT metadata inspection, VirtualDevice/VDA and Appium for repeatable remote testing. ADBT's manifest, media, focus and build skills are discoverable and should ground the P5 prompt assessment; skill discovery itself is not device qualification. Amazon Content Launcher, Media Controls and DRM/MSE may be relevant to future creator needs, but this audit found no requirement to add them to the bounded P5 remote-manifest objective.

## 11. Recommended Correction Work

1. In P5 prompt assessment, include F-01 as a contract gate and explicitly test informational writing, playable audio/video, asset rights, redaction and incompatible schema behavior. Do not redesign `ChannelSpec` or collapse catalog/publication duties.
2. Build a small installed-TV manifest client with HTTPS fetch, bounded parse, compatibility check, immutable sequence/pointer discipline, persisted last-known-good, safe startup and rollback. Test network failure and incompatible revision before VirtualDevice qualification. Keep private S3/evidence and signed URL capabilities out of public manifests.
3. Add F-03 player lifecycle/error behavior only to the extent needed for truthful TV playback; test remote focus/Back after failure and background/resume on target. Keep URL mode scoped to nonadaptive MP4/MP3 unless a licensed adaptive use case justifies MSE.
4. Carry F-02/F-04 into P7 build/release lineage; carry F-06 and S1–S6 into preproduction hosting. Do not pull those operations into P5 merely to close unrelated historical gates.
